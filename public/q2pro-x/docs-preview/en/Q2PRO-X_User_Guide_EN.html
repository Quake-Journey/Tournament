Release 1.0 updates relative to beta 0.99

Release 1.0 finalizes the modern cvar browser as a real end-user feature. RU/EN switching, search, copy, resize, scroll, and browser-local text scale now belong to one coherent tool.

Overlay gear buttons are now part of the standard workflow. Server browser, cvar browser, mod overlay, and LAGHAX HUD can all open their own settings directly from inside the overlay.

The LAGHAX HUD gained its own alpha path and an optional runtime block for weapon-predict diagnostics. That runtime block is off by default and exists for observation, not for gameplay changes.

The 1.0 package also makes the data layer explicit: both menu files, q2pro.modhelp, and the browser-local font atlas are mandatory runtime resources.

Release 1.0 updates

The 1.0 line is built around polish, coherence, and delivery discipline. Features are no longer described as isolated experiments but as parts of a stable client layer with documentation, menus, release notes, and website presentation.

The most visible result is the modern cvar browser, but the same thinking also shaped overlay return flow, package contents, bilingual help surfaces, and the branding layer used across the release.

Modern cvar browser

The modern cvar browser is now a full in-game reference surface. It supports RU/EN descriptions, resize by mouse, search, copy actions, browser-local scale, and independent alpha.

Players can inspect variables in a readable way without leaving the game or relying on old text files and memory.

Settings from overlays

Every modern overlay now exposes a gear button. Clicking it opens the relevant settings page instead of forcing manual menu navigation.

Closing that page returns the user to the exact overlay they came from, which keeps the overlay layer coherent.

LAGHAX HUD and weapon-predict diagnostics

The HUD now owns its own alpha setting and no longer hides a dependency on scr_alpha.

An optional runtime block for weapon-predict state exposes existing internal state visually but does not alter weapon behavior, fire rate, or server authority.

What matters about the 1.0 release package

Q2PRO-X 1.0 continues the additive-layer philosophy. The package should ship the client layer itself, not a generated personal config.

Generated q2pro-x.cfg is still not part of the public package, while the menu files, mod-help data, and browser font atlas are mandatory release assets.

1. What Q2PRO-X is and why this client exists

Q2PRO-X is an evolution of Q2PRO shaped by the ideas, testing scenarios, and practical priorities of ly. The goal is not to collect random cvars, but to turn long-requested Quake II client improvements into one coherent user-facing layer.

The project exists because useful workflows were historically fragmented across old forks, private scripts, rare pak files, and forum knowledge. Q2PRO-X tries to gather those directions into one controlled and documented client.

2. What the previous beta line contained

The pre-1.0 beta line was built as a clean release layer. It shipped the Q2PRO-X runtime and data folder rather than replacing a user's whole Quake II installation.

That approach protected testers from accidental overwrite scenarios and made it easier to reason about what exactly belonged to Q2PRO-X.

2.1. What changed in beta 0.97 (previous wave)

Beta 0.97 established several pillars that still matter in 1.0: practical 4:3 pillarbox handling, more mature predict follow-up work, richer LAGHAX HUD visibility, and step-smoothing fixes for lift behavior.

It also reinforced release discipline: cleaner package contents, stronger documentation, and clearer explanations of what changed for testers between waves.

3. Quick practical start

The fastest way to understand Q2PRO-X is to open the guided menu and walk through the top-level sections once. That gives a player an overview of the major systems without forcing them to remember old cvar names.

For a first session, the most useful places to visit are LAGHAX, Weapon Predict, Movement & Physics, Sound & Acoustics, Display & Capture, and the modern server browser.

4. Network features: what they do and how to use them

The network-facing comfort layer in Q2PRO-X is built around LAGHAX and related diagnostics. Its purpose is to make unstable links feel less brutal without pretending that the server stopped correcting the client.

The LAGHAX HUD exists so the user can see what the client is reacting to instead of treating smoothing as invisible magic.

4.1. R1Q2-like movement feel: what it changes in practice

R1Q2-like feel is one of the compatibility-oriented client behavior paths in Q2PRO-X. It changes how movement is perceived locally and is useful for players trained on older Quake II client expectations.

It does not turn the client into a server cheat. The point is familiarity and comfort, not bypassing server physics authority.

5. Video and graphics: what is actually new

Q2PRO-X turns display handling into a real user-facing subsystem. This includes modern window mode, desktop fullscreen, classic fullscreen, 4:3 pillarbox behavior, render tuning, highlight-related controls, and OLED-aware options.

The practical benefit is that players no longer have to rely on fragile manual resolution hacks just to get clean 4:3 presentation or desktop-friendly fullscreen behavior on modern monitors.

5.1. How to set 4:3 and 800x600

The intended workflow is to use the display/video pages in the Q2PRO-X menu rather than manual trial-and-error through vid_modelist or old fullscreen assumptions.

For classic 4:3 play, the important distinction is whether the player wants desktop fullscreen, exclusive fullscreen, or a true window. Q2PRO-X exposes those paths directly.

6. Sound: how to enable it and how the layers differ

Sound in Q2PRO-X is split into meaningful layers instead of being treated as one flat volume field. The client exposes OpenAL behavior, binaural and HRTF options, reverb/acoustics, resampler-related choices, and practical sound-category controls.

That matters because not every player wants the same thing: some care about clean positional cues, some about room character, and some about desktop-friendly focus behavior.

7. Highlights: what they are for in practice

Highlight and visibility controls exist because real players often need more readable scenes than the default game provides. Q2PRO-X exposes those controls as explicit user-facing options rather than hidden experimental states.

The practical role of highlights is readability. They are meant to help the player parse important objects and actors more easily, not to turn the client into a wallhack-style tool.

8. Modern server browser

The modern server browser is a real overlay window, not just an old server list with a new paint job. It supports multi-field search, sorting, filtering, details tabs, and direct connection flow.

The legacy browser remains available as a fallback. Q2PRO-X adds a modern browser without forcing every player to abandon the older path.

9. Mod Command Overlay

The mod overlay is especially useful on servers such as OpenTDM and OpenFFA. It groups commands by purpose, supports prompt-style commands, and surfaces practical spectator and voting actions without forcing players to memorize syntax.

This makes it valuable not only for ordinary players but also for casters, streamers, and anyone who needs quick access to repeated server-side actions.

13. Full overview of the Q2PRO-X menu

This section exists for ordinary users who simply want to know where to look. If you open Q2PRO-X and need a practical map of the menu layer, start here.

By 1.0 the menu tree is stable enough to describe as a product rather than a moving target.

13.1. Q2PRO-X / Global settings

Global settings contain options that should follow the player across mods and play contexts. Display behavior, global overlays, browser settings, audio layers, and other client-wide choices generally belong here.

13.2. Q2PRO-X / Local mod settings

Local mod settings are for behavior that should remain tied to the current gamedir or gameplay environment rather than following the player globally.

13.3. Q2PRO-X / Config

The Config section remains the central place for q2pro-x.cfg workflow, autosave behavior, return to defaults, and user-facing safety switches such as Alt+F4 behavior.

13.4. Q2PRO-X / Mod overlay

This page controls how the mod overlay behaves, which command groups remain visible, and how the overlay fits a streamer, caster, or player workflow.

13.5. Q2PRO-X / Server browser

This page controls the modern browser behavior itself and keeps browser UX separate from the legacy server list model.

14. Where the key features came from

Q2PRO-X does not hide the origin of good ideas. It openly acknowledges when user-facing workflows were inspired by older client traditions, R1Q2 habits, Q2PRO legacy behavior, or modern expectations built up during testing.

15. OLED protection and safe pillarbox for OLED panels

By the later beta line, classic 4:3 pillarbox handling was treated not only as a convenience feature but also as a panel-safety feature for modern OLED screens.

The system can animate pillarbox bars, fade the whole screen on inactivity, and modulate interface transparency in OLED-oriented scenarios without overwriting a player's ordinary alpha choices.

16. What mattered specifically in beta 0.97

Beta 0.97 mattered because it closed several unpleasant prediction and movement problems while making LAGHAX and overlay diagnostics easier to trust.

A lot of the later 1.0 confidence came from this stage: multiple systems stopped behaving like isolated beta experiments and started behaving like maintained client features.

16.1. Weapon predict follow-up: hyperblaster, machinegun, chaingun

One of the nastier beta problems involved hyperblaster and related continuous-fire behavior. The follow-up work reduced visual mismatch and strengthened how local prediction is paired with authoritative state.

16.2. LAGHAX HUD: visible enabled state

The HUD evolved into a more trustworthy surface by showing what is actually enabled instead of making users infer state from memory.

16.3. R1Q2-style step smoothing on lifts

Lift jitter under R1Q2-like step smoothing was one of the movement issues that needed real debugging rather than guesswork. The fix matters because vertical movement edge cases can quickly destroy trust in compatibility modes.

15. Beta 0.98 updates relative to 0.97

Beta 0.98 pushed several systems from interesting to maturing. Display mode semantics, sound behavior on focus loss, OLED behavior, stabilized weapon-predict architecture, LAGHAX starvation handling, and server browser favorites all moved forward.

15.1. Display & Capture: windowed mode

Window mode became a deliberate product feature rather than a side effect of old fullscreen handling. This matters for desktop workflows, streaming, and testing.

15.2. Automatic sound handling on focus loss and OLED idle

Q2PRO-X added optional sound behavior for focus loss and OLED-idle situations so the client cooperates better with real desktop use.

15.3. OLED protection: what matters now

By this stage OLED protection was no longer only about static side bars. It became a wider display-care branch with idle behavior, UI-related opacity handling, and practical usability refinements.

15.4. Weapon predict: what changed for the player

For the player, the important change was a cleaner, more trustworthy predict experience. Hidden-gun cases, handoff behavior, and continuous-fire edge cases became less surprising and more product-like.

15.5. LAGHAX: low-ping server-to-client starvation

Q2PRO-X also investigated starvation-like feel on low-ping but bad-delivery situations. This reflects the broader philosophy behind LAGHAX: comfort work should care about real-world network ugliness, not only obvious high-ping scenarios.

15.6. Modern Server Browser: Favorites without manual file editing

Favorites became a normal browser workflow rather than something hidden behind manual file editing or awkward maintenance habits.

0.99 updates (for testers)

Beta 0.99 was the bridge into release 1.0. It brought guided menu mode, broader browser and cvar-reference work, additional overlay polish, and the stronger product presentation that later became the public 1.0 website and documentation layer.
