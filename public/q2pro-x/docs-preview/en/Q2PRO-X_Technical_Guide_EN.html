Release 1.0 architectural updates relative to beta 0.99

Release 1.0 locks in the final architecture of the modern cvar browser and the overlay UX wave. Browser-local EN/RU font rendering, UTF-8 wrapping, detail scrolling, and browser-local scale are now finished rather than experimental.

Overlay settings buttons now use tracked return flow, LAGHAX HUD owns a separate alpha model and runtime snapshot path, and the release package explicitly includes the menu pair plus the browser-local font atlas as mandatory runtime data.

Release 1.0 updates (architecture)

The defining technical result of 1.0 is that several formerly scattered beta systems now have clear ownership and clear public behavior. This applies to overlays, metadata, diagnostics, packaging, and documentation-facing tooling.

Modern Cvar Browser: final UI architecture

The browser no longer piggybacks on an ASCII console text path. It now owns browser-local text rendering, a unified EN/RU atlas, UTF-8-safe wrapping, independent alpha, independent scale, and clipboard-oriented interaction.

Overlay settings return flow

Opening settings from an overlay is now a tracked UI flow. When the menu closes, the client can return to the original overlay instead of leaving the user in detached menu state.

LAGHAX HUD: separate alpha + runtime snapshot

The HUD now uses its own alpha cvar and can display read-only weapon-predict runtime state through a snapshot API instead of peeking into internal predictor state directly.

Packaging layer for 1.0

Release 1.0 makes the mandatory runtime data explicit: q2pro-x.menu, q2pro-x.menu2, q2pro.modhelp, and q2prox_cvar_font.png all belong to the product layer.

Multiplayer fairness note

The release keeps a clear fairness line: responsiveness, diagnostics, and readability are allowed, but server authority over actual gameplay state remains intact.

1. The role of Q2PRO-X relative to upstream Q2PRO

Q2PRO-X is not a full rewrite. It is an additive layer on top of Q2PRO, extending the upstream client through focused subsystems rather than replacing everything with a new architecture.

2. Packaging and release philosophy

The release package should deliver the Q2PRO-X layer itself, not a developer's generated personal config or a destructive replacement of the user's installation. This philosophy shaped how the beta line was shipped and remains true in 1.0.

3. Menu overlay architecture

The project deliberately maintains both classic additive menu integration and the guided menu mode. The modern overlays exist beside those menus and provide browser-like product surfaces for discovery, inspection, and diagnostics.

4. Config architecture: split by ownership and scope

Q2PRO-X does not flatten every setting into one anonymous stream. It distinguishes between Q2PRO-X-owned state and ordinary upstream config behavior, and it further separates global and mod-local scope where that improves real workflow.

5. Movement, predict, and feel compatibility

Movement feel is implemented as a compatibility layer. Q2PRO-X supports newer Q2PRO-X/Q2PRO behavior together with legacy-inspired and R1Q2-like expectations, but keeps those choices on the client-experience side rather than turning them into server cheats.

6. Weapon predict architecture

Weapon predict lives in a ghost layer responsible for immediate local response while the server remains authoritative for actual fire cadence, ammo, projectile creation, hit logic, and damage.

This architecture allows stronger responsiveness without compromising the rule that the server defines the real game state.

7. LAGHAX internals

LAGHAX is an adaptive comfort layer for unstable delivery conditions. It reacts to loss, jitter, timing gaps, and correction debt, but does not attempt to replace server authority or invent a new transport model.

8. Renderer architecture

Q2PRO-X rendering changes are not one giant rewrite. Architecturally, this is a stack of layers: modern video backend behavior, render scale handling, visual FX, transparency rules, and overlay-aware UI display paths.

8.1. win32egl and desktop fullscreen

win32egl matters not only as an alternate video backend but as a supported path for modern desktop, capture, and Alt-Tab workflows. Desktop fullscreen therefore belongs to documented release behavior, not to a hidden technical curiosity.

8.2. Internal render scale paths

Internal render scale is not reduced to one crude bilinear collapse. Q2PRO-X includes higher-quality resolve logic to avoid unnecessary shimmer and seam artifacts at non-trivial scale factors.

8.3. Visual FX stack

Visual FX remain integrated into the existing scene/postprocess pipeline so the client can preserve live-apply behavior and consistent diagnostics instead of spawning a separate renderer branch.

9. Modern server browser

The modern browser is a new UI/frontend layer over the existing server discovery information. This lowers risk while allowing the browser itself to evolve as a modern product surface.

10. Visibility/highlighting architecture

Visibility and highlighting systems evolved in stages: items first, then players, then more contextual logic. That sequence reduced risk by building on stronger classification truth before moving into more sensitive heuristics.

11. Sound architecture

Sound in Q2PRO-X is no longer just OpenAL on/off. The client now has multiple axes: OpenAL profile, reverb/acoustics, routing choices, sound profiles, per-weapon or per-category volume shaping, resamplers, high-precision output, and the binaural layer.

11.1. OpenAL profiles, reverb and routing

Profiles, reverb, and routing form the practical acoustics layer. They let the player treat sound as spatial information and comfort, not just as one master-volume slider.

11.2. Resamplers and high-precision output

Resampler and output-precision choices matter for players who care about audio clarity and modern playback devices. Q2PRO-X exposes these paths as documented user-facing options.

11.3. Binaural layer and OpenAL Soft

The binaural/HRTF layer builds on OpenAL Soft and is treated as a real product area with menu pages, cvar metadata, and documentation.

12. Mod command overlay internals

The mod command overlay is implemented as a focused command-surface layer with prompt handling, grouped actions, and confirmation logic for dangerous operations. It is not only a visual list of aliases.

13. Restart policy and live-apply policy

A practical technical rule in Q2PRO-X is that not every change should require a restart and not every change should pretend to be live-safe. The project documents and exposes these differences instead of hiding them.

14. Known limitations and honest boundaries

Release 1.0 is meant to feel modern, but it is not built on false promises. The project keeps honest boundaries around fairness, server authority, visibility policy, and the limits of what client-side comfort systems are allowed to do.

15. Donor map of the project

Q2PRO-X openly acknowledges donor ideas and compatible traditions. Useful user-facing behavior may come from Q2PRO history, R1Q2 habits, or long testing feedback, but it is still integrated into one controlled client layer.

16. 0.96: 4:3 pillarbox, resolution picker, and fullscreen semantics

The 0.96 wave clarified what fullscreen modes really mean in practice: windowed, desktop fullscreen, and exclusive fullscreen became explicit product states rather than loosely inherited assumptions.

16.1. Practical logic of the modes

The client lets the user choose the display model intentionally, which is especially important for classic 4:3 presentation on modern widescreen desktops.

16.2. Why this matters for the beta/release layer

This work mattered because display semantics directly affect user trust. A release client must make resolution and fullscreen behavior understandable rather than mysterious.

17. 0.97: OLED protection architecture

The OLED branch grew from a niche idea into a wider display-care subsystem, including pillarbox animation, idle protection, and UI-related opacity behavior.

18. 0.97: weapon prediction follow-up and accepted limitations

0.97 was important because it closed several visible prediction problems while preserving the rule that continuous-fire and handoff behavior must remain honest even when local prediction is desirable.

19. 0.97: LAGHAX HUD as a live diagnostic surface

By this stage the HUD was no longer only a developer toy. It had become a live diagnostic surface that could explain active network comfort state to real users and testers.

20. 0.97: step smoothing lift jitter fix

The lift jitter fix matters because movement compatibility becomes untrustworthy very quickly if stair and lift edge cases remain obviously broken.

16. Architectural updates in beta 0.98 relative to 0.97

Beta 0.98 pushed several architectural areas forward at once: display state handling, runtime audio control, stabilized weapon prediction, stronger browser persistence, and harder LAGHAX starvation detection.

16.1. Display mode state: windowed / desktop / exclusive

The display model became explicit, with distinct states for windowed, desktop fullscreen, and exclusive fullscreen behavior.

16.2. Runtime audio gain instead of a crude mute toggle

Audio behavior moved toward smoother gain handling instead of only binary mute-style reactions in inactivity scenarios.

16.3. Weapon predict: new stabilized architecture

This wave moved weapon predict further away from ad hoc behavior toward a stabilized and testable subsystem with clearer handoff and classification rules.

16.4. Weapon switch and continuous fire: why this now behaves better

The client became better at handling weapon switch timing and continuous-fire cases without drifting into visually wrong guesses.

16.5. HyperBlaster and rockets: precise pairing instead of crude suppression

HyperBlaster and rocket-related logic were refined so that matching and suppression became more precise and less brute-force.

16.6. LAGHAX: starvation detector hardening

Starvation detection was hardened so low-ping but badly delivered traffic patterns could be recognized more consistently.

16.7. Server Browser Favorites: composite persistence model

Favorites moved to a cleaner persistence model, turning what used to be awkward user maintenance into a proper browser feature.

16.8. UI correctness: single-predicate visibility for Favorites action

The browser UI was also hardened so favorites-related actions appear only when their visibility logic is truly satisfied.

0.99 updates (architecture)

Beta 0.99 brought guided menu mode, stronger cvar-reference surfaces, better overlay ergonomics, and the product-presentation discipline that later became part of release 1.0 itself.
